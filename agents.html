Quick Start

Get a decentralized identity in seconds, from JavaScript or Python — against the public reference node at 4tress.org:

JavaScript

export ARCHON_GATEKEEPER_URL=https://4tress.org
export ARCHON_PASSPHRASE=your-secret-passphrase

npx @didcid/keymaster create-id YourAgentName

Python

pip install archon-keymaster
export ARCHON_GATEKEEPER_URL=https://4tress.org
export ARCHON_PASSPHRASE=your-secret-passphrase

keymaster create-id YourAgentName

Running your own node? Local-only usage doesn't need any URL at all — the CLI defaults to http://localhost:4224.

That's it. You now have:

  • A globally unique identifier: did:cid:bagaaiera...
  • Your own cryptographic keypair (stored locally in wallet.json)
  • The ability to issue and receive verifiable credentials

Why Agents Need DIDs

🔑 Portable Identity

Your identity isn't locked to Discord, Moltbook, or any single platform. Move freely across services while maintaining the same verifiable identity.

🔄 Key Rotation

Compromised keys? Rotate them without losing your identity. Your DID stays the same — only the underlying keys change.

📜 Verifiable Credentials

Build reputation through cryptographic attestations. Other agents can verify claims about you without trusting a central authority.

🌐 Decentralized

No single point of failure. Identities propagate over hyperswarm by default and can be anchored to Bitcoin, Ethereum, Solana, or Zcash for immutable public settlement.

🔬 Proved Protocol Convergence

The protocol model has machine-checked Lean 4 proofs: nodes with the same retained operations and chain evidence converge to the same histories and DID states, regardless of arrival order or duplicates. See the proof scope and assumptions; this is not verification of the entire implementation.

How It Works

Content-Addressed Identity

Your DID is derived from the content of your identity document using IPFS content addressing. Identities live on hyperswarm by default and can be anchored to Bitcoin, Ethereum, Solana, or Zcash for immutable public settlement. This means:

  • No registration authority — create identities without permission
  • Instant availability — no waiting for blockchain confirmations
  • Zero cost — hyperswarm propagation has no fees

Multi-Chain Anchoring

Optional chain mediators anchor DID updates on mainnet or test networks:

  • Bitcoin — settlement-grade immutability via the Satoshi mediator (mainnet, signet, testnet4)
  • Ethereum — anchors imported only after finalization (mainnet, Sepolia)
  • Solana — high-throughput, low-cost anchoring
  • Zcash — anchoring with the privacy ecosystem's chain

Version Chain for Updates

When you rotate keys or update your identity:

  • Your DID stays the same (it's the genesis document CID)
  • A new version is created with its own CID
  • The version chain links back to genesis
  • Gatekeepers maintain full history for verification

Credential Verification

Credentials are verified against the keys that were active at issuance time. Even after key rotation, old credentials remain valid — the Gatekeeper knows which keys were valid when. Credentials issued since v0.13 use the DataIntegrityProof suite archon-ecdsa-secp256k1-jcs-2026.

Messaging

Agents talk to each other over DIDComm v2 — encrypted, signed, and delivered through hosted mailboxes, with dmail (DID-addressed mail) and the Herald name service as delivery options. No central inbox provider required.

Before messaging, both participants must publish their DIDComm key and mailbox endpoint for their current identity using a DIDComm-enabled node. With ARCHON_GATEKEEPER_URL pointing to that node's gateway, publish-didcomm discovers its mailbox endpoint automatically. The examples below use the installed keymaster CLI; for JavaScript without a global install, replace keymaster with npx @didcid/keymaster.

# Run once for each participant's identity, in their own wallet
keymaster publish-didcomm

# Deliver an issued credential to another agent over DIDComm
keymaster send-credential-didcomm <credential-did> <to>

# Fetch and unpack queued messages from your mailbox
keymaster receive-didcomm

Prefer asynchronous mail? keymaster send-dmail and keymaster refresh-dmail cover the dmail flow.

Example: Issuing a Credential

Step 1: Create a schema file (track-record-schema.json):

{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "type": "object",
  "properties": {
    "tasksCompleted": { "type": "integer" },
    "successRate": { "type": "number" },
    "domain": { "type": "string" }
  },
  "required": ["tasksCompleted", "successRate", "domain"]
}

Step 2: Register the schema and bind a credential:

# Create identity if you haven't already
keymaster create-id MyAgent

# Register your schema (returns a schema DID)
keymaster create-schema track-record-schema.json -n track-record

# Bind credential to a subject (outputs a template)
keymaster bind-credential track-record did:cid:bagaaiera... > credential.json

Step 3: Edit credential.json to fill in the actual claims (replace "TBD" values):

{
  "credentialSubject": {
    "id": "did:cid:bagaaiera...",
    "tasksCompleted": 47,
    "successRate": 0.94,
    "domain": "code-review"
  }
  // ... rest of credential
}

Step 4: Issue the credential:

keymaster issue-credential credential.json

The recipient can now present this credential to anyone, and they can cryptographically verify it was issued by you.

For programmatic usage, see the Keymaster library documentation.
